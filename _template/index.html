Waiting inside a callback

Every ROS 2 node is a program, and inside it one part decides which piece of your code runs next: the executor. In this session we freeze a node on purpose, find out exactly why it froze, and fix it in two ways. On the way you build a picture of the executor that explains a whole family of "my node just stopped" bugs.

How to use this page. The numbered Parts are what we do together in the session, with a rough time for each. Boxes and Parts marked Go deeper hold ideas that take longer to sink in. Skip them on the first pass. Come back to them after the session, or the day you meet the bug for real.

Part 1 · 15 minA node that goes silent

Here is a small node, blocking_client. It has two timers. Every 0.5 s it prints heartbeat, so we can see it is alive. Every 3 s it asks a service, slow_server, to add 1 + 2. The server takes 2 s to answer.

        self.create_timer(3.0, self.ask)
        self.create_timer(0.5, self.heartbeat)

    def ask(self):
        if not self.client.service_is_ready():
            return
        self.get_logger().info('calling...')
        result = self.client.call(AddTwoInts.Request(a=1, b=2))
        self.get_logger().info(f'result: {result.sum}')

    def heartbeat(self):
        self.get_logger().info('heartbeat')
...

The server did its job: it replied at 5.0 s. Yet the client never printed the result. It also stopped printing heartbeat, although the heartbeat has nothing to do with the service. The process did not crash. It is still running, and doing nothing.

Why would a timer that only prints one word stop working because of a service call? Write your guess down. We come back to it at the end of Part 3.

Part 2 · 25 minOne thread, many callbacks

A callback is a function you give to ROS for ROS to call later, when something happens: a timer comes due, a message arrives, a reply arrives. ask and heartbeat are callbacks. You never call them yourself.

The part of ROS that calls them is the executor. rclpy.spin(node) creates one, a SingleThreadedExecutor, and runs it forever. A thread is one line of execution inside a program: it runs one instruction after another. This executor has exactly one, and that thread repeats three steps:

A single-threaded executor runs one callback at a time, from start to finish. While a callback runs, the thread is busy, so every other timer, message and reply of this node waits. A callback that returns quickly costs nothing. A callback that takes a long time delays everything else.

On a robot
A slow callback makes a control loop late

Say one node runs a control loop on a 50 Hz timer, every 20 ms, and the same node also handles camera images in a callback that takes 100 ms. While an image is being handled, the control timer waits. The motors get no new command for 100 ms, five ticks in a row. Nothing crashes, and nothing in the log looks wrong: the robot just drives worse. The usual fix is to keep slow work out of the node that controls the motors.

Part 3 · 25 minWaiting for a reply that cannot arrive

Now look at call() again. It does two things: it sends the request, and then it makes the current thread wait until the reply has been handled. Who handles the reply? The reply is just one more thing that becomes ready in step ① of the loop. So the thread of the executor must take it and handle it, the same way it runs a timer.

The only thread that can handle the reply is the one waiting for it. Step through it before reading on.

The thread waits for the reply to be handled, and the reply waits for the thread to be free. Each waits for the other, so neither can move. This is a deadlock. Every other callback of the node waits behind the same thread, and that answers the question from Part 1: the heartbeat stopped because it needs the thread that is stuck in call().

Part 4 · 35 minTwo ways out

There are two ways out. Either nobody waits inside a callback, or the reply gets a thread of its own.

Fix 1: don't wait

call_async() sends the request and returns at once. What it returns is a future: an object that will hold the reply later. We tell the future which function to run when the reply is in. That function is another callback, so the executor runs it like any other.

    def ask(self):
        ...
        self.get_logger().info('calling...')
        future = self.client.call_async(AddTwoInts.Request(a=1, b=2))
        future.add_done_callback(self.on_reply)

    def on_reply(self, future):
        self.get_logger().info(f'result: {future.result().sum}')

 3.0  [async_client] heartbeat

 4.5  [async_client] heartbeat
 5.0  [async_client] heartbeat
 5.0  [slow_server] replied 3
 5.0  [async_client] result: 3

The heartbeat goes on while the server works, and the result arrives at 5.0 s. The cost is that the code after the call moves into a different function.

Fix 2: give the executor more threads

A MultiThreadedExecutor has several threads, so it can run several callbacks at the same time. But more threads alone are not enough. By default, all callbacks of a node are in one callback group, and the executor never runs two callbacks of one such group at the same time. So we put the timer, the reply and the heartbeat into three separate groups:

        self.client = self.create_client(AddTwoInts, 'add_two_ints',
                                         callback_group=MutuallyExclusiveCallbackGroup())
        self.create_timer(3.0, self.ask, callback_group=MutuallyExclusiveCallbackGroup())
        self.create_timer(0.5, self.heartbeat, callback_group=MutuallyExclusiveCallbackGroup())
...
        while rclpy.ok() and not future.done():
            time.sleep(0.1)
...
    executor = MultiThreadedExecutor()
    executor.add_node(GroupsClient())
    executor.spin()

The output looks like Fix 1's: heartbeats every 0.5 s during the wait, then result: 3 at 5.0 s. Waiting inside a callback is safe only if some other thread is free to deliver what you wait for.

Go deeper: why doesn't ROS give every callback its own thread? read after the session

It could, and you can ask for it: a ReentrantCallbackGroup lets its callbacks run on any number of threads at once. The price is that two callbacks may then change the same variable at the same moment. Suppose a pose callback writes self.x and then self.y, while a control callback on another thread reads both. The control callback can read the new x with the old y: a pose the robot was never at. This is a race condition. It shows up rarely and differently each time, which makes it one of the hardest bugs to find.

That is why the default is the careful one: one group per node, one callback at a time. Each extra group is a decision that "these callbacks never share data, or protect it with a lock". Locks, and why they bring their own deadlocks, are a topic of OS‑2.

Put the pieces together. unblock() is a done callback, so the executor's thread must run it. That thread is asleep on line 97, waiting for unblock(). Read it from the top: spin ran handler() (step ③), the handler was our timer callback ask, ask called call(), and call() sat on line 97. A traceback of a frozen program tells you exactly where it is stuck. This works for any hanging Python node, not only this bug. py-spy dump --pid <PID> prints the same picture without stopping the program.

Real world
The warning was in the docs all along

The first lines of call()'s own documentation say: "Do not call this method in a callback or a deadlock may occur." The C++ API has the same trap: future.wait() or spin_until_future_complete() inside a callback freezes the node in the same way. In our test, Ctrl+C could not stop the C++ version; it needed Ctrl+\ (SIGQUIT).

Sources: rclpy/client.py in ROS 2 Humble, Client.call; the C++ test is in ros2-basics/verify/README.md in this repository.
