Files and Processes檔案與 process

Every node you start is a Linux process, and the Linux kernel decides how it starts, how it stops and what it may touch. In this session we start a small robot stack, try to stop it, and fail. Then we find out why. On the way you learn the operating-system ideas behind most "it won't stop", "it died when SSH dropped", "permission denied" and "works on my machine" problems: processes, signals, daemons, file permissions and shared libraries.

你啟動的每個 node 都是一個 Linux process，而 Linux 核心決定它怎麼啟動、怎麼停止、可以碰什麼。這堂課我們啟動一個小小的機器人系統，試著把它停掉，結果失敗了；然後找出原因。過程中你會學到大部分「停不下來」、「SSH 一斷就死掉」、「permission denied」、「在我電腦上可以跑」問題背後的作業系統觀念：process、signal、daemon、檔案權限和共享函式庫。

Part 1第 1 部分You stopped it. It's still running.你停掉它了，它還在跑

Part 2第 2 部分Inside the computer電腦裡面

Before we look at processes, here is the hardware they run on. You only need four things that hold data and one thing that does the work. Every later Part (and every later course) leans on this picture.

在看 process 之前，先看它們跑在什麼硬體上。你只需要知道四個存放資料的地方，和一個做事的東西。後面每個部分（以及後面每堂課）都會用到這張圖。

The CPU runs instructionsCPU 執行指令

To the CPU, a program is a long list of very simple instructions: load a number, add two numbers, compare, jump to another place in the list. A core is one part of the CPU that runs instructions one after another, driven by a clock: 2.9 GHz means 2.9 billion ticks a second, and a simple instruction takes about one tick. A core works on registers: a few dozen slots inside the core, each holding one number. One register, the program counter, holds which instruction is next.

對 CPU 來說，程式是一長串非常簡單的指令：載入一個數字、把兩個數字相加、比較、跳到清單的另一個位置。核心（core）是 CPU 裡一個接一個執行指令的部分，由時脈驅動：2.9 GHz 代表每秒 29 億次 tick，一個簡單的指令大約花一次 tick。核心在暫存器（register）上工作：核心裡面幾十個小格子，每格放一個數字。其中一個暫存器（program counter）記著下一個要跑的指令在哪裡。

A CPU has several cores, so several programs really run at the same moment. The laptop we ran this course's examples on:

一顆 CPU 有好幾個核心，所以好幾個程式真的可以在同一刻一起跑。我們跑這堂課範例的筆電：

$ lscpu     # selected lines
CPU(s):                                  16
Thread(s) per core:                      2
Core(s) per socket:                      8
CPU max MHz:                             2901.0000
L1d cache:                               256 KiB (8 instances)
L2 cache:                                4 MiB (8 instances)
L3 cache:                                8 MiB (2 instances)

8 cores, each able to run 2 streams of instructions, so Linux sees 16 CPUs. The cache lines come next.

8 個核心，每個能同時跑 2 串指令，所以 Linux 看到 16 個 CPU。cache 那幾行接下來會說明。

Where data lives: fast and small, or big and slow資料放在哪：快而小，或大而慢

A core can only compute on what is in its registers, so data must be brought in from somewhere. There are four levels, and each step down is bigger, cheaper and slower:

核心只能運算暫存器裡的東西，所以資料得從某個地方搬進來。一共有四層，每往下一層就更大、更便宜、也更慢：

  • Registers: inside the core. A few hundred bytes. Ready within the tick.暫存器：在核心裡面。幾百個位元組。在同一個 tick 內就能用。
  • Cache: on the CPU chip, in levels L1, L2 and L3. Kilobytes to megabytes. It keeps copies of what was used recently, automatically: programs never manage it.快取（cache）：在 CPU 晶片上，分成 L1、L2、L3 三層。KB 到 MB 等級。它會自動保留最近用過的資料的副本：程式從來不用管它。
  • RAM: separate chips next to the CPU. Gigabytes. Holds every running program and its data. Emptied at power off.RAM：CPU 旁邊獨立的晶片。GB 等級。放著每個正在跑的程式和它的資料。斷電就清空。
  • SSD: storage. Hundreds of gigabytes. Holds files, and keeps them when the power is off.SSD：儲存裝置。數百 GB。放檔案，斷電後還在。

How much slower? We measured it on the same laptop. memory_latency.cpp follows a chain of pointers through arrays of growing size, so every read waits for the one before. A small array stays in the cache; a big one only fits in RAM. A second small program read 4 KiB at random places in a 1 GiB file on the SSD, bypassing the cache:

慢多少？我們在同一台筆電上量過。memory_latency.cpp 在越來越大的陣列裡沿著一串指標走，所以每次讀取都要等前一次。小陣列會留在快取裡；大陣列只放得進 RAM。另一個小程式在 SSD 上一個 1 GiB 的檔案裡隨機讀 4 KiB，不經過快取：

     128 KiB     4.1 ns per read      fits in L2
    1024 KiB    11.6 ns per read      fits in L3

A read from the SSD takes as long as about 40,000 reads from the cache. That is why a program is copied from the SSD into RAM before it runs, and why the cache exists at all: most of the time, the next thing a program needs is close to the last thing it used, and the cache already has it.

從 SSD 讀一次的時間，大約可以從快取讀 40,000 次。這就是為什麼程式要先從 SSD 複製到 RAM 才能執行，也是快取存在的理由：大部分時候，程式下一個需要的東西就在它剛用過的東西附近，而快取裡已經有了。

The kernel shares all of this核心負責分配這一切

Hundreds of programs want the same cores, the same RAM and the same devices. The Linux kernel is the program that hands them out: which program runs on which core and for how long, which part of RAM belongs to whom, who may use which device. Every other program has to ask the kernel. The rest of this course is about the kernel's rules: for running programs (processes), for stopping them (signals), and for files and devices (permissions).

幾百個程式都想用同樣的核心、同樣的 RAM、同樣的裝置。Linux 核心就是負責分配的那個程式：哪個程式在哪個核心上跑、跑多久，RAM 的哪一塊屬於誰，誰可以用哪個裝置。其他每個程式都得去問核心。這堂課接下來講的，就是核心的規則：關於正在跑的程式（process）、關於停止它們（signal），以及關於檔案和裝置（權限）。

On a robot在機器人上
Two computers, the same ideas兩台電腦，同樣的觀念

A robot usually carries two kinds of computer. The robot computer runs Linux and ROS: a multi-core CPU, gigabytes of RAM, an SSD, and often a GPU (on Jetson-class boards the GPU shares the same RAM). The microcontroller (MCU) drives the motors and reads the encoders: one core at a few hundred MHz, around a megabyte of RAM, no SSD (its program sits in flash memory, which keeps it at power off), and no Linux. The levels and the trade-offs are the same; only the numbers shrink. The fake serial port in this course stands for the wire between them.

機器人通常帶著兩種電腦。機器人電腦跑 Linux 和 ROS：多核心 CPU、好幾 GB 的 RAM、SSD，常常還有 GPU（在 Jetson 這類板子上，GPU 跟 CPU 共用同一塊 RAM）。微控制器（MCU）驅動馬達、讀 encoder：一個幾百 MHz 的核心、大約 1 MB 的 RAM、沒有 SSD（程式放在 flash 記憶體裡，斷電也還在），也沒有 Linux。層級和取捨都一樣，只是數字變小。這堂課裡的假序列埠，代表的就是它們之間的那條線。

Part 3第 3 部分A node is a processnode 就是一個 process

A program is a file; a process is a program running程式是檔案；process 是正在跑的程式

driver.py is a file on the SSD. So is /usr/bin/python3, the program that runs it, and so are the ROS libraries it uses. To run a program, the kernel copies it from the SSD into RAM (Part 2 showed why) and gives it a core to run on. The running program, together with everything the kernel keeps track of for it, is a process.

driver.py 是 SSD 上的一個檔案。跑它的程式 /usr/bin/python3 也是，它用到的 ROS 函式庫也是。要跑一個程式，核心會把它從 SSD 複製到 RAM（第 2 部分說明了為什麼），再給它一個核心去跑。正在跑的程式，加上核心為它記錄的一切，就是 process。

The kernel gives every process a number, the PID (process ID). Every node is one process, with its own PID. Two nodes in one launch are two processes; the same node started twice is two processes, too.

核心給每個 process 一個編號：PID（process ID）。每個 node 都是一個 process，有自己的 PID。一個 launch 裡的兩個 node 是兩個 process；同一個 node 啟動兩次，也是兩個 process。

What a shell isshell 是什麼

When you open a terminal, the window only shows text. The program you are actually typing to is a shell, usually bash. A shell does one job, over and over: read a command, start the program you named, wait until it finishes, then show the prompt ($) again. The shell is a process, and so is every program it starts for you.

打開終端機時，那個視窗只負責顯示文字。你真正在對它打字的程式叫 shell，通常是 bash。shell 一直重複做一件事：讀一個指令、啟動你指定的程式、等它結束，然後再顯示提示字元（$）。shell 是一個 process，它幫你啟動的每個程式也都是。

Every process has a parent每個 process 都有父 process

A process never appears out of nothing: another process starts it, and that one is its parent. Linux does this in two steps, and it is easiest to see in code. Here is everything a shell does with one command, in C. The command is fixed to ps, which lists processes:

process 不會憑空出現：一定是另一個 process 啟動它，那個 process 就是它的父 process（parent）。Linux 分兩步完成這件事，用程式碼看最清楚。下面是 shell 處理一個指令時做的全部事情，用 C 寫的。指令固定是 ps：列出 process 的程式。

    printf("parent: I am PID %d\n", getpid());

    pid_t child = fork();

    if (child == 0) {
        printf("child:  I am PID %d, my parent is PID %d\n",
               getpid(), getppid());
        execlp("ps", "ps", "-o", "pid,ppid,cmd", NULL);
        perror("exec failed");
        return 1;
    }

    waitpid(child, NULL, 0);
    printf("parent: child %d has ended, back to me\n", child);

把滑鼠移到標起來的那幾行，可以看到說明。完整檔案在 code/tiny_shell.c。

We compiled it and ran it from bash:

我們把它編譯好，在 bash 裡執行：

$ gcc -o tiny_shell /code/tiny_shell.c && ./tiny_shell

Follow the numbers. bash (PID 20) started tiny_shell (27). fork made a copy, 28, whose parent is 27. In the copy, exec replaced the program with ps, but the process stayed the same: ps lists itself as PID 28. The parent waited, and printed its last line only after the child had ended.

跟著數字看。bash（PID 20）啟動了 tiny_shell（27）。fork 複製出一份 28，它的父 process 是 27。在複製出來的那份裡，exec 把程式換成 ps，但 process 還是同一個：ps 列出的自己就是 PID 28。父 process 一直在等，等子 process 結束後才印出最後一行。

Every program you start from a terminal is started this way: the shell forks, the copy execs your program, and the shell waits. ros2 launch does the same once for every program in the launch file, except that it doesn't wait for one before starting the next: they run side by side. So processes form a tree, and ps --forest draws it:

你從終端機啟動的每個程式都是這樣啟動的：shell 先 fork，複製出來的那份 exec 你的程式，shell 再等它。ros2 launch 也一樣，對 launch 檔裡的每個程式各做一次，只是它不會等前一個結束才啟動下一個：它們同時在跑。所以 process 會排成一棵樹，ps --forest 會把它畫出來：

PPID is the parent's PID. bash (20) started the launcher (36), and the launcher started all three programs. The launcher is the parent of every node it starts. Remember that for Part 4.

PPID 是父 process 的 PID。bash（20）啟動了 launcher（36），launcher 再啟動了三個程式。launcher 是它啟動的每個 node 的父 process。第 4 部分會用到這件事。

/proc: ask the kernel/proc：直接問核心

Where did ps get those PIDs and parents? From the kernel, which keeps a record of every process and shows it as files in /proc: one folder per PID.

ps 是從哪裡拿到這些 PID 和父 process 的？從核心。核心幫每個 process 留著紀錄，並把它當成檔案放在 /proc 裡：每個 PID 一個資料夾。

$ ls /proc     # only the numbered folders
1  7  13  20  36  37  39  41  ...
$ grep -E '^(State|PPid|VmRSS|Threads)' /proc/39/status
State:	S (sleeping)
PPid:	36
VmRSS:	   52932 kB
Threads:	11

The driver (39) is sleeping until its next timer, its parent is the launcher (36), it uses about 52 MB of RAM, and it runs 11 threads. These files are not on the SSD: the kernel writes them out at the moment you read them. ps and top do nothing more than read /proc. Part 8 shows more of it.

driver（39）在睡覺，等下一次 timer；它的父 process 是 launcher（36），用了大約 52 MB 的 RAM，有 11 條執行緒。這些檔案不在 SSD 上：是你讀的那一刻，核心才把它們寫出來。ps 和 top 做的也只是讀 /proc。第 8 部分有更多。

Part 4第 4 部分Stopping a process: signals停止 process：signal

Nothing outside a process can reach into it and stop it. Instead, the kernel delivers it a signal: a short notice with a number and a name. kill is the command that asks the kernel to send one; despite its name, it only sends a notice. These are the signals you will meet:

process 外面的東西沒辦法伸手進去把它停掉。取而代之的是，核心送給它一個 signal：一個帶編號和名字的簡短通知。kill 就是請核心送 signal 的指令；雖然叫 kill，它只是送一個通知。你會遇到的 signal 有這些：

Every one of them ends the process by default. But a process can catch a signal: tell the kernel "when this one arrives, run my function instead". A node catches SIGINT to shut down cleanly. Go deeper: zombies, and why docker run --init exists延伸：zombie，以及為什麼有 docker run --init read after the session課後再讀

When a process ends, the kernel keeps a small record of it, its exit code, until its parent reads it with wait(). Until then the process is a zombie: dead, but still in the table. The launcher's log line "process has died [..., exit code -2]" is the launcher reading that record. Orphans are adopted by PID 1, and a normal PID 1 (systemd, or tini in a container started with --init) reads their records too. But if PID 1 is a program that never calls wait(), zombies pile up. Our first test container ran sleep infinity as PID 1, and after a few experiments it looked like this:

process 結束時，核心會保留它的一小筆紀錄（exit code），直到它的父 process 用 wait() 讀走。在那之前，這個 process 是 zombie：已經死了，但還留在表裡。launcher 的 log「process has died [..., exit code -2]」就是 launcher 讀到了這筆紀錄。孤兒由 PID 1 收養，正常的 PID 1（systemd，或用 --init 啟動的容器裡的 tini）也會讀走它們的紀錄。但如果 PID 1 是一個從不呼叫 wait() 的程式，zombie 就會越積越多。我們第一個測試容器用 sleep infinity 當 PID 1，做了幾次實驗之後變成這樣：

    PID    PPID TT       CMD
    362       1 ?        [ros2] <defunct>
    363       1 ?        [python3] <defunct>
    365       1 ?        [python3] <defunct>
    367       1 ?        [python3] <defunct>
    ... 19 more

Zombies use no CPU or memory, only a PID each. But a container that runs for weeks can run out. docker run --init (or init: true in compose) puts a tiny PID 1 in front of your program that does nothing but pass signals on and read exit codes.

zombie 不用 CPU 也不用記憶體，只各佔一個 PID。但跑了好幾個禮拜的容器可能會用完。docker run --init（或 compose 裡的 init: true）會在你的程式前面放一個很小的 PID 1，它只做兩件事：把 signal 傳下去、讀走 exit code。

Go deeper: strace, watching a process talk to the kernel延伸：strace，看 process 跟核心對話 read after the session課後再讀

Afterwards ls -l /proc/PID/fd lists it as 15 -> /dev/pts/1:

Go deeper: stable device names with udev rules延伸：用 udev rule 取得固定的裝置名稱 read after the session課後再讀

Plug in two USB serial adapters and they become /dev/ttyUSB0 and /dev/ttyUSB1, in whatever order they were detected, which can change at the next boot. udev is the daemon that creates device files when hardware appears, and a udev rule tells it to add a fixed name, a symlink, chosen by something unique to the device: its USB vendor and product ID, or its serial number. That is the same idea as our /tmp/mcu → /dev/pts/0. A rule can also set the group and mode, which solves Part 6 for that one device:

Go deeper: permission bits as numbers延伸：用數字表示權限位元 read after the session課後再讀

Each rwx group is three bits: r = 4, w = 2, x = 1. So rw- is 6, r-x is 5, and crw-rw---- is mode 660. chmod 660 file sets all three groups at once; chmod g+rw file changes only what you name. 每組 rwx 是三個位元：r = 4、w = 2、x = 1。所以 rw- 是 6，r-x 是 5，crw-rw---- 是權限 660。chmod 660 file 一次設定三組；chmod g+rw file 只改你指定的部分。另外還有三個很少用到的位元：setuid（程式以它的擁有者身分執行，sudo 就是這樣變成 root 的）、setgid，以及 sticky 位元（在 /tmp 上：任何人都能在裡面建檔案，但只有擁有者能刪除）。
